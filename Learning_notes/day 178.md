## 1. What Is Deployment?

Deployment means making an application available online so other people can access it.

Until now, we have mainly run our API locally using:

```bash
npm run dev
```

This runs our application on our own computer.

After deployment, users can access our API through a public URL.

Example:

```text
http://localhost:5000/api/projects
```

After deployment:

```text
https://your-api.onrender.com/api/projects
```

## 2. What Happens When We Deploy an API with a Database?

Our application has two main parts:

1. Backend API – handles requests and application logic.
2. Database – stores application information.

When deploying, both parts must communicate correctly.

### Application architecture

```text
        User
          |
          v
      Frontend
          |
          v
    Express API
          |
          v
      Mongoose
          |
          v
     MongoDB Atlas
```

### Understanding the flow

1. A user sends a request.
2. Express receives the request.
3. The controller processes it.
4. The service communicates with MongoDB through Mongoose.
5. MongoDB returns the requested information.
6. Express sends a response to the user.

## 3. Local Database vs Cloud Database

### Local database

A local database runs on your computer.

Example:

```text
mongodb://127.0.0.1:27017/learning_tracker
```

Advantages:
- Useful for development.
- Works without an internet connection.
- Easy to test locally.

Disadvantages:
- Other servers cannot automatically access it.
- Your database is tied to your local environment.

### Cloud database

MongoDB Atlas hosts our database online.

Example:

```text
mongodb+srv://USERNAME:PASSWORD@CLUSTER.mongodb.net/learning_tracker
```

Advantages:
- Accessible to deployed applications.
- Data is stored independently of your local computer.
- Useful for production applications.

## 4. Connecting a Deployed API to MongoDB Atlas

Our API needs a MongoDB connection string.

We store it in an environment variable.

Inside `.env`:

```env
MONGO_URI=your_mongodb_connection_string
PORT=5000
NODE_ENV=development
```

In our application:

```js
require("dotenv").config();

const mongoose = require("mongoose");

const connectDB = async () => {
  try {
    await mongoose.connect(process.env.MONGO_URI);

    console.log("MongoDB connected successfully");
  } catch (error) {
    console.error("Database connection failed:", error.message);
    process.exit(1);
  }
};

module.exports = connectDB;
```

The application uses `process.env.MONGO_URI` instead of exposing database credentials inside the source code.

## 5. Environment Variables in Production

A common deployment mistake is assuming that the local `.env` file automatically moves to the hosting platform.

It does not.

We must configure environment variables separately in the hosting provider.

For example, in Render:

| Variable | Example |
|---|---|
| MONGO_URI | MongoDB Atlas connection string |
| NODE_ENV | production |
| PORT | Usually provided automatically |

Never upload your real `.env` file to GitHub.

## 6. What Is a Hosting Platform?

A hosting platform provides computers and infrastructure to run applications online.

Examples:

- Render
- Railway
- Fly.io
- AWS
- Microsoft Azure

For our learning project, we can use Render to deploy the Express API.

Deployment steps:

1. Push the project to GitHub.
2. Create a web service.
3. Connect the GitHub repository.
4. Configure the build command.
5. Configure the start command.
6. Add environment variables.
7. Deploy the application.
8. Test the public API URL.

## 7. Prepare package.json for Deployment

Our `package.json` should contain a production start command.

Example:

```json
{
  "scripts": {
    "start": "node server.js",
    "dev": "nodemon server.js"
  }
}
```

Understanding the commands:

- `npm start` runs the production application.
- `npm run dev` runs the development application.

The hosting platform normally uses `npm start`.

## 8. Database Network Access

Even when our API is deployed, MongoDB Atlas must allow it to connect.

MongoDB Atlas has Network Access settings.

We need to:

1. Open MongoDB Atlas.
2. Navigate to Network Access.
3. Review allowed IP addresses.
4. Configure access for the hosting environment.
5. Check database user permissions.

For production, restrict network access as much as your hosting infrastructure allows.

## 9. Deployment Errors

Some common deployment problems include:

| Error | Possible reason |
|---|---|
| MongoDB connection failed | Incorrect connection string |
| Authentication failed | Incorrect database credentials |
| Network access denied | Hosting environment not allowed |
| Application failed to start | Incorrect start command |
| Module not found | Missing dependency |
| 404 error | Incorrect API route |
| Environment variable missing | Variable not configured in hosting platform |

Server logs help us identify these problems.

## 10. Test the Deployed API

After deployment, the hosting platform provides a public URL.

Example:

```text
https://your-api.onrender.com
```

Test the following endpoints using Postman:

```text
GET /api/projects
```

```text
GET /api/projects?page=1&limit=5
```

```text
GET /api/projects?sort=oldest
```

```text
GET /api/projects?title=Learning
```

We should also test creating, updating, and deleting records.

A successful deployment should allow the API to communicate with MongoDB Atlas and return the expected responses.
